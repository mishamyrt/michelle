# План разработки и внедрения дизайн-системы Michelle

Дизайн-система развивается по второму варианту: готовые контролы, семантические модификаторы и повторяющиеся композиции поверх GPUI. Состояние, события, layout и жизненный цикл остаются в GPUI и существующих моделях приложения.

Размер текста интерфейса фиксирован и определяется системными стилями macOS. Пользователь может менять размер контента; это не увеличивает подписи, иконки, отступы и контролы интерфейса. Удаление настройки масштаба интерфейса входит в первый этап разработки.

Статус на 13 октября 2026 года: код этапов 1–8 внедрён; итоговая очистка API и документации выполнена. Контракты контролов, разделение UI/контента, формы Settings/Skills, общие commit/goal dialogs, навигация, панели выбора, статусы, загрузка и переведённые горячие пути проверены компилятором и тестами. Performance gate этапа 7 для полного приложения остаётся открытым: сняты изолированные counters и стоимость компонентов, но cadence и CPU реального streaming не измерены. Визуальная проверка не запрошена и не проведена; этим документом она не разрешается. Раздел 2 описывает исходное состояние до разработки, статусы этапов фиксируют историю внедрения. Актуальный API описан в src/ui/README.md.

## 1. Какой результат нужен

Экран должен описывать структуру и действия, а библиотека — оформление и стандартное поведение контролов. Изменение общей кнопки, строки формы или поверхности должно применяться ко всем переведённым экранам через один компонент.

Целевой пример:

```rust,ignore
use crate::ui::prelude::*;

Section::new("Отображение")
    .description("Настройки ответов")
    .child(
        Surface::new()
            .child(
                FormRow::new("Математические формулы")
                    .description("Показывать формулы в ответах")
                    .control(
                        Toggle::new("render-math", self.state.render_math)
                            .on_change(cx, |this, enabled, _, cx| {
                                this.set_render_math(enabled, cx);
                            }),
                    ),
            ),
    )
```

Критерии результата:

- Общие контролы имеют согласованные конструкторы, размеры, состояния и обработчики.
- Строки настроек, действия, диалоги и пустые состояния собираются из компонентов.
- Оформление имеет определённый порядок переопределения; настройки builder не исчезают при рендере.
- Пользовательский ввод, операции с провайдерами, данные и их сохранение работают через прежние модели.
- Клавиатура, фокус и reduce-motion сохраняются при переводе экранов; масштаб контента отделён от фиксированной типографики интерфейса.
- Изменение размеров текста сообщений и кода не меняет размеры интерфейсных подписей, иконок, контролов и layout chrome.
- Работа одного кадра зависит от видимого содержимого; композиция не добавляет I/O или новые источники постоянной перерисовки.
- Компонент можно расширить в его модуле без изменения глобального реестра, собственного DSL или нового UI runtime.

## 3. Границы системы

### В `src/ui`

- Общие цвета, типографика, размеры, иконки и primitives.
- Представление стандартных состояний: disabled, loading, selected, highlighted, invalid, focused — только там, где они применимы.
- Поведение контролов: активация, обработка клавиш, видимый фокус, правила событий вложенных действий.
- Композиции интерфейса: строки формы, поверхности, секции, строки действий, модальные оболочки.
- Существующие механизмы меню, размещения, прокрутки и движения.

### У владельца экрана

- Значения полей, selection, cursor/highlight, expanded, pending, ошибки и проверки данных.
- `Entity<TextInput>`, долговременные `FocusHandle`, menu handles и состояния прокрутки.
- Запросы, подписки, таймеры операций, generations, сохранение и бизнес-правила.
- Переизмерение виртуализированных строк и существующие правила кэширования панелей.
- Локализованные подписи, сведения о провайдерах и предметные статусы.
- Решение о том, можно ли выполнить действие в момент события.

Компоненты принимают готовое содержимое и обработчики. Они не обращаются к `Michelle`, `ProviderKind`, сессиям, git, daemon или хранилищу настроек. Предметные компоненты вроде `ModelPicker`, `BranchPicker`, composer и tool activity остаются в `src/app` и используют общие детали.

### За пределами этой разработки

Не добавлять собственный `View`/`Binding` runtime, diff дерева, универсальный reducer, proc-macro DSL, систему плагинов стилей, новый layout engine или автоматическое управление состоянием. Не переносить `src/input.rs`, редактор, Markdown и терминал только ради структуры папок. Не менять протокол, БД, темы пользователей и закреплённую ревизию GPUI. В persistence допускается описанное ниже переименование настройки размера текста с сохранением сериализованного ключа и значения; остальные данные не мигрируют.

Собственные `List` и `ScrollView`, универсальная таблица, сетка, slider и radio group не входят в обязательный набор: обследование не показало задачи, ради которой их нужно реализовать сейчас.

## 4. Устройство модулей

```text
src/ui/
├── mod.rs                  # Фасад и совместимые реэкспорты
├── prelude.rs              # Публичные компоненты и нужные GPUI traits
├── appearance.rs           # Активный UiColors и generation
├── ui_colors.rs            # Разрешённые цвета общих контролов
├── tokens/                 # Палитра, типографика, общие размеры
├── icons/                  # SF Symbols и SVG
├── layout.rs               # h_stack, v_stack, spacer
├── components/
│   ├── mod.rs
│   ├── button.rs           # Сначала сохранять текущие файлы
│   ├── toggle.rs
│   ├── text_field.rs
│   ├── surface.rs
│   ├── divider.rs
│   ├── section.rs
│   ├── form_row.rs
│   ├── action_row.rs
│   ├── dialog/             # Делить только после появления нескольких обязанностей
│   └── menu/               # Развивать существующую реализацию
└── primitives/             # activation, navigation, motion, scrollbar, squircle
```

Это целевая схема ответственности, а не список файлов для создания заранее. Небольшой компонент остаётся в одном файле. Растущий компонент делится на builder/сборку, оформление и поведение; фасад содержит объявления и экспорты. Отдельный общий каталог `styles` не нужен, пока оформление удобно держать рядом с компонентами.

Зависимости:

```text
tokens + UiColors + icons + primitives
                 ↓
             controls
                 ↓
            compositions
                 ↓
             app screens

src/theme → Theme::ui_colors() → appearance
```

Загрузка темы и применение снимка происходят снаружи UI. Компоненты читают готовые цвета из памяти. Существующий `TextInput` остаётся внутренней зависимостью оболочек ввода; его постепенное отделение от `Theme` не является условием первого этапа.

## 5. Публичный API

### Конструирование и композиция

- Stateless-компонент: `#[derive(IntoElement)]` и `RenderOnce`.
- Интерактивный компонент получает стабильный `ElementId`; для повторяющихся строк ID опирается на идентичность данных, а не на подпись или позицию после сортировки.
- Контейнер с произвольным числом детей реализует `ParentElement` и поддерживает `.child()`/`.children()`.
- Именованные места содержимого, например `FormRow::control`, принимают `impl IntoElement` и хранят элемент в форме, которую уже использует GPUI. Отдельную систему slots не создавать.
- `h_stack()`, `v_stack()` и `spacer()` возвращают обычный `Div`. Это семантические помощники без дополнительной entity или второго layout-узла.
- `Styled` сохраняет доступ к GPUI layout. `InteractiveElement` добавляется там, где он нужен для композиции событий и существующих menu helpers; универсальный trait для всех компонентов не вводить.

Пример контролов:

```rust,ignore
Button::new("save", tr!("common.save"))
    .button_style(ButtonStyle::Primary)
    .control_size(ControlSize::Regular)
    .disabled(self.pending)
    .track_focus(&self.save_focus)
    .on_activation(cx, |this, window, cx| {
        this.save(window, cx);
    });

IconButton::new("refresh", SfSymbol::new("arrow.clockwise"))
    .loading(self.pending)
    .disabled(self.pending)
    .tooltip(tr!("common.refresh"))
    .on_activation(cx, |this, _, cx| this.refresh(cx));
```

### Имена методов

| Метод | Контракт |
| --- | --- |
| `.control_size(ControlSize)` | Размер контрола; не конфликтует с GPUI `.size(...)` |
| `.button_style(ButtonStyle)` | Визуальный вариант кнопки; не конфликтует с `Styled::style` |
| `.role(ButtonRole)` | Смысл действия: обычное или destructive |
| `.text_style(TextStyle)` | Семантическая типографика |
| `.disabled(bool)` | Блокировка действия и соответствующее отображение |
| `.loading(bool)` | Индикатор операции; сам по себе не определяет разрешение действия |
| `.selected(bool)` | Выбранное значение |
| `.highlighted(bool)` | Текущая строка клавиатурной или указательной навигации |
| `.track_focus(&FocusHandle)` | Использование стабильного фокуса владельца |
| `.on_activation(cx, handler)` | Единая активация мышью и немодифицированными Enter/Space |
| `.on_change(cx, handler)` | Предложение нового значения контролом выбора |

Методы реализуются только у подходящих компонентов. Например, `Label` не получает `.disabled`, а `FormRow` не становится кликабельным контейнером из-за наличия контрола справа.

Первый этап сохраняет названия `ButtonStyle::Primary`, `Secondary` и `Ghost`. Семантическое разделение не требует переименовать все варианты ради сходства со SwiftUI. Старый `Destructive` сохранялся до появления эквивалентной комбинации style + role с тем же оформлением; на этапе 8 неиспользуемый вариант удалён. Использовать `Secondary` с `ButtonRole::Destructive`.

### Совместимость

Добавлять новый API рядом с текущим, затем переводить вызывающий код небольшими группами.

- На этапах 1–7 `.style(...)` и `.size(...)` у `Button` временно делегировали новым именам. На этапе 8 неиспользуемые aliases удалены; канонический API — `button_style`, `control_size` и `role`.
- Сохранять `ui::menu`, `ui::sidebar`, `ui::motion`, существующие функции и реэкспорты до перевода их callers.
- Не менять незаметно возвращаемый тип используемых `icon_button` и `toolbar_button_segment`: экраны используют GPUI traits и fluent methods этих типов. `toggle_switch` сохранял свой тип до удаления на этапе 8, когда вне compatibility-теста callers уже не осталось.
- Совместимые функции и новые builders должны использовать общую внутреннюю сборку оформления там, где это позволяет сохранить сигнатуры. Старый helper может принимать явный `UiColors`, а новый builder получать снимок при render.
- Перед удалением старого API проверить исходники, тесты и README через `rg`. Deprecation включать после перевода callers, чтобы не оставлять постоянные предупреждения в проекте.
- Экспортировать публичный компонент через `components/mod.rs`, `ui/mod.rs` и `prelude.rs` в той же задаче, где появляется его использование.

## 6. Оформление и токены

### Порядок разрешения стиля

Порядок одинаков для контролов:

1. Базовая структура и оформление по умолчанию.
2. Выбранные размер, визуальный вариант и роль.
3. Явные настройки builder и GPUI `StyleRefinement` вызывающего кода.
4. Оформление текущего состояния и интерактивных переходов.
5. Обязательные гарантии поведения: disabled не активируется, фокус остаётся видимым.

Различать настройки вида и обработчики событий. Слияние `StyleRefinement` не должно менять ID, потерять children или скопировать/заменить handlers.

В `Button::render` и аналогичных оболочках сначала сохранить refinement, заданный вызывающим кодом, собрать defaults, затем применить сохранённый refinement механизмом GPUI. Вместо постоянного клонирования всего компонента использовать перемещение данных; дополнительные структуры добавлять только для реально разделённых параметров.

Контрольные примеры:

- `.h(px(40.0))` перекрывает высоту выбранного `ControlSize`.
- `.px(px(12.0))` не теряется после применения стандартного padding.
- `.bg(custom_color)` меняет обычный фон; hover/pressed для этой поверхности остаются согласованными с разрешённым фоном.
- Установка `.disabled(true)` до или после handler даёт одинаковое поведение.
- Порядок `.role(...)` и `.button_style(...)` не меняет смысл комбинации.

Явные hover/active-настройки вызывающего кода нужно сохранить. Если обёртка не может совместить их с собственным оформлением, определить ограничение в API и добавить поддерживаемый способ настройки состояния, а не молча перезаписать его. Пользовательский стиль не снимает обязательный focus-visible и блокировку disabled.

Оформление конкретного компонента разрешается небольшой локальной функцией из `UiColors`, размера, роли и его состояний. Не вводить глобальную таблицу всех комбинаций и публичный протокол стилей на первом этапе.

### Цвета

- Сохранить `Palette` как исходные абстрактные цвета и `UiColors` как готовый снимок общих ролей.
- Для status-компонентов добавить `success` и `warning` в `UiColors`; заполнить их в light/dark defaults и `Theme::ui_colors()` из уже существующих полей `Theme`.
- При добавлении поля найти все `UiColors { ... }` и обновить их в той же задаче.
- Не добавлять обязательные поля в TOML ради компонентов. Файлы пользовательских тем должны продолжить загружаться без изменений.
- Surface принимает общий вариант поверхности или явный цвет. Цвета `canvas`, `composer`, `terminal` и предметные gauge-роли остаются у приложения.
- Сохранять generation при применении темы. Тема обновляет весь снимок до refresh; кэши, чувствительные к цветам, используют generation в существующем порядке.

### Типографика и размеры

#### Фиксированный интерфейс

`TextStyle::size()` и `line_height()` остаются в логических единицах GPUI (`Pixels`), независимых от настроек контента. Эти единицы соответствуют размерам layout, а не физическим пикселям дисплея: Retina/DPI обрабатывает GPUI. Фиксированный размер не означает принудительно одинаковое число физических пикселей на разных экранах.

Использовать существующую системную семью `.SystemUIFont`, семантические роли и их обычные macOS-размеры, веса и межстрочные расстояния. Роли `Body`, `Caption`, `Headline`, `Title1–3` сопоставить с macOS text styles; опираться на Apple HIG и AppKit, а не переносить размеры iOS. Apple указывает 13 pt как обычный размер текста macOS и 10 pt как минимальный ориентир; это не требование свести все роли к одному размеру. [Typography HIG](https://developer.apple.com/design/human-interface-guidelines/typography).

Таблицу ролей закрепить в `tokens/typography.rs` после сверки с системными стилями. Если для точного сопоставления нужны метрики AppKit, получить их один раз при инициализации платформы и сохранить готовые значения в памяти; вызовы `NSFont` не должны попасть в render или row builder. Для справки использовать [NSFont.preferredFont(forTextStyle:options:)](https://developer.apple.com/documentation/appkit/nsfont/preferredfont(fortextstyle:options:)) и [NSFont.systemFontSize](https://developer.apple.com/documentation/appkit/nsfont/systemfontsize). Размеры интерфейса не вычисляются из `content_font_size` или `code_font_size`.

В первом этапе `window.rem_size` уже зафиксирован на прежней технической базе 14, независимо от пользовательских настроек: старые `sp(value)` дают исходный логический размер. Значение 14 здесь — совместимая база единицы rem, а не размер системного `Body`. Постепенно заменить оставшиеся старые UI-вызовы `sp()` на `TextStyle` или явные `px()` для геометрии; удалить helper и совместимые реэкспорты после перевода callers. Не менять его возвращаемый тип или значения всех `rem`-размеров GPUI ради этой миграции.

Новые компоненты сразу используют `TextStyle` для типографики и `px()`/метрические токены для геометрии. Не допускаются ни прямые вызовы `sp()`, ни зависимость от него через общие helpers; при переиспользовании такого helper сначала перевести его геометрию на пиксельные размеры. `sp()` исключён из `ui::prelude` и остаётся только для совместимости старых callers. SF Symbols, SVG/file icons и spinner используют `px()`; rem-база не служит промежуточной реализацией новых компонентов.

Проверить также `sp()` для размеров provider marks и другой геометрии, `text_sm`/`text_base`, унаследованный шрифт input и все `set_rem_size`: изменение размера контента не должно обходным путём увеличивать chrome. Не добавлять новый масштабируемый путь типографики в `Label` или `StyledTypography`.

Фиксированные размеры контролов, иконок, отступов и высот строк определяются собственными ролями и `ControlSize`. `ControlSize::Small`/`Large` — варианты дизайна для конкретного места, а не пользовательский zoom. Особые inset и геометрию capsule хранить рядом с компонентом; общий токен добавлять только при повторном использовании.

Начальные размеры переносимых поверхностей фиксировать по исходному UI при стандартных настройках. Дробные размеры, например 13,5, затем сопоставить с выбранными системными ролями в явном изменении оформления. Не менять глобальный Body ради одной строки; результат нормализации должен быть одинаковым на всех экранах, использующих эту роль. Сохранять легибельность, системный шрифт и запас для вертикальных метрик разных письменностей.

#### Масштабируемый контент

Отдельные метрики контента разрешаются в приложении и передаются в текстовую поверхность как явные размеры в `px()`. Размер содержимого может менять высоту его блока и требовать переизмерения виртуализированного списка; размеры окружающих контролов остаются фиксированными.

| Поверхность | Правило |
| --- | --- |
| Sidebar, toolbar, tabs, menus, формы, picker rows, badges, подсказки клавиш | Фиксированные роли UI; пользовательский размер контента не участвует |
| SearchField и однострочные поля настроек | Фиксированная типографика UI; ввод остаётся в `TextInput` |
| Сообщения, reasoning, Markdown-файлы и текст SKILL.md | `content_font_size`; контентные line height, block gaps и формулы следуют его метрикам |
| Code blocks, file editor, diff и mono tool output | Существующий `code_font_size` и собственные метрики |
| Пользовательский текст composer, objective и commit message | Контент; передать метрики явно, не масштабировать заголовки диалогов, actions и обрамление поля |
| Inline code и код внутри Markdown | Сохранить существующее разделение prose/code размеров; проверить совместный layout |
| Toast, сообщения интерфейсной ошибки, подписи и действия возле контента | Фиксированный UI, даже когда для выделения текста используется Markdown renderer |
| Изображения и терминал | Сохранить самостоятельную геометрию/zoom изображений и текущие терминальные метрики; глобальный UI zoom на них не распространяется |

Общая оболочка `TextArea` принимает контентный стиль извне. Режим single-line/multi-line сам по себе не определяет масштаб: назначение поверхности задаёт владелец. Вспомогательный `scaled_markdown_metrics` разделить по назначению: контентные callers используют настраиваемые метрики, UI-callers — фиксированные. В частности, `render_toast` сейчас вызывает тот же helper, что и контент; этот вызов нужно перевести на фиксированные метрики без потери выделения и копирования.

#### Замена настройки масштаба интерфейса

Минимальное совместимое изменение:

1. В `AppSettings` и `PersistedState` переименовать Rust-поле `ui_font_size` в `content_font_size`, default и sanitizer — соответственно в `DEFAULT_CONTENT_FONT_SIZE` и `sanitized_content_font_size`. Сохранить исходный default контента 14 и существующую проверку конечности/диапазона.
2. Сохранить сериализованный ключ `ui_font_size` через `#[serde(rename = "ui_font_size")]`: это только прежнее имя на диске для размера контента. Значение больше не влияет на UI. Такой переход не требует переписывать настройки и позволяет откатить код без потери предпочтения. Новое имя ключа на диске не входит в этот этап.
3. Обновить default constructors, `app_settings`, `apply_app_settings`, загрузку старого единого state и тесты. Старое значение, например 18, после обновления продолжает увеличивать контент; интерфейс возвращается к фиксированным системным размерам. Не сбрасывать значение пользователя до 14.
4. В Appearance заменить «Размер шрифта интерфейса» на «Размер текста контента» с описанием фактических поверхностей. Обновить `locales/app.yml`, `locales/ru.yml`, IDs/handles и остальные существующие локали, если в них есть эти ключи. Настройку `code_font_size` сохранить.
5. Заменить `set_ui_font_size` на `set_content_font_size`: сохранить save, notify и необходимое переизмерение контента, убрать изменение `window.rem_size`. На старте окна не читать размер контента для rem-базы.
6. В `MarkdownMetrics::scaled/document`, transcript, file preview, Skills и остальных callers заменить зависимость от UI на явный размер контента. Проверить текст composer и многострочных dialog inputs, которые раньше могли наследовать размер через окно.
7. Обновить fingerprints/кэши и `remeasure_font_sized_surfaces` по фактическим контентным зависимостям. Смена размера контента инвалидирует его измерения, math layout и нужные текстовые кэши; не пересчитывает фиксированные sidebar rows и контролы.
8. Обновить UI README и комментарии, где `sp()` или `window.rem_size` описаны как пользовательский масштаб интерфейса. Проверить также UI-команды/shortcuts: любые существующие действия масштаба текста должны менять соответствующий контент, а не root окна. Не добавлять новые zoom-команды ради этого перехода.

На первом этапе меняется только смысл прежней настройки и её Rust/API-имя. Переименование ключа JSON потребует отдельного решения о совместимости; пока legacy-ключ явно документируется. `.control_size()` и системное масштабирование дисплея не являются настройкой масштаба интерфейса.

### Скругления

`overflow_hidden` в GPUI обрезает прямоугольник. Surface и Dialog не должны обещать автоматическую маску по своему радиусу. Детям с фоном, изображением или hover-слоем у края нужно дать собственные соответствующие радиусы с учётом рамки. В split button сохранить существующее округление внутреннего paint и возможность меню рисоваться вне capsule.

## 7. Поведение, фокус и жизненный цикл

### Действия

Переиспользовать `ActivationExt`, `activation_listener` и `with_activation`. Для новых Button, IconButton, ActionRow и boolean-контролов подключать семантический handler после разрешения disabled, а не безусловно при вызове builder.

Каждая активация выполняет действие один раз. Модифицированные сочетания остаются за actions/key bindings экрана. На вложенных независимых действиях остановить propagation, чтобы закрытие вкладки не активировало вкладку, а кнопка в строке не выполняла действие строки.

Наличие `.disabled()` не блокирует произвольный `.on_click`, который вызывающий код добавил через `InteractiveElement`. У кнопок канонический путь действия — `on_activation`; низкоуровневые обработчики подключать только с явной проверкой состояния. Проверить также обработчики, которые добавляет композиция меню, а не сам контрол.

Владелец повторно проверяет pending и предметные ограничения в handler: состояние могло измениться после построения элемента. `on_change` передаёт предложенное значение из отображаемого состояния; контрол не хранит второй источник истины. Если операция зависит от самого свежего значения, handler читает текущую модель или используется действие toggle через `on_activation`.

### Фокус и клавиатура

- Использовать стабильные IDs и существующие `FocusHandle` владельца; не создавать focus handle на каждый render.
- Каждый mouse-контрол имеет клавиатурный способ действия и видимый focus-visible.
- Группировать формы, меню и диалоги через GPUI `tab_group`/`tab_stop`/`tab_index`.
- Для boolean-контролов поддержать Space/Enter; для menus и выбора — стрелки и принятые в проекте Home/End/Escape; для tabs и disclosure — соответствующую навигацию.
- При временном disabled не терять текущий фокус. Политику tab order переносить осознанно: нынешний `toggle_switch` остаётся в порядке Tab, а некоторые action rows исключают disabled из него.
- Элементы, появляющиеся на hover, должны становиться доступными при клавиатурном фокусе. Это особенно важно для действий сообщения и favorite внутри строки модели.
- Не кодировать статус только цветом: отображать подпись или иконку вместе с цветом.

### Ввод

`TextField`, `SearchField` и `TextArea` принимают уже созданный `Entity<TextInput>`. Placeholder, IME, cursor, selection, undo, clipboard, режим Enter и содержимое принадлежат этому input. Оболочка не пересоздаёт input, не подписывается заново и не меняет его содержимое из render.

`SearchField` задаёт поисковую иконку и оформление; debounce, поиск, clear-on-Escape и результаты определяет владелец. `TextArea` использует multi-line input, размеры viewport и существующую прокрутку.

В первой версии не добавлять `.disabled()` к оболочке ввода, если она лишь уменьшает opacity. Когда такой API понадобится, связать визуальное состояние с реальным запретом редактирования в input и отдельно проверить клавиатуру, paste и IME. `read_only` сохраняет выделение и копирование; его нельзя автоматически приравнять к полной блокировке. Изменение режима input выполняется владельцем при смене состояния через существующий `set_read_only`, а не при каждом render.

### Диалоги и popover

Dialog принимает стабильный handle/фокус, содержимое и callbacks confirm/dismiss. Экран хранит draft, pending и операции; закрытие оболочки не отменяет уже запущенный commit или goal operation.

Сначала перенести оболочку с сохранением нынешнего deferred-слоя и порядка фокусировки. В текущих goal/commit dialogs фокус ставится после двух кадров, потому что deferred surface ещё должна войти в dispatch tree. Не заменять этот порядок предположением о синхронном mount.

Сохранить Escape, клик по scrim, остановку mouse propagation внутри card, клавиши подтверждения, порядок Tab и возврат фокуса после закрытия. При быстром закрытии или замене диалога отложенная фокусировка не должна попасть в старый input: проверять identity/generation открытого диалога перед callback.

Menus и popover продолжают использовать существующий `ContextMenuHandle`. Для Picker использовать отдельный trigger focus и фокус menu card; для searchable popover сохранять фокус его TextInput. Весь handle не создавать заново в builder.

Сейчас `anchored_surface` добавляет mouse/key handlers самостоятельно и не получает disabled-состояние триггера. Поэтому Picker должен передавать доступность в общую внутреннюю сборку меню, где блокируются оба способа открытия. Старые helpers сохраняют сигнатуры и прежний enabled по умолчанию. Если открытый Picker становится недоступным, его владелец закрывает menu handle при смене состояния; render не выполняет это действие. Покрыть тестом и открытие disabled-триггера, и отключение уже открытого меню.

### 8.2. Раскладка и формы

| Компонент | Контракт и устройство |
| --- | --- |
| `h_stack`/`v_stack` | Возвращают `Div` с нужным flex-направлением; gap, alignment, sizing — GPUI |
| `spacer` | Возвращает один существующий layout-элемент с flex grow |
| `Surface` | Владеет фоном, рамкой, радиусом и padding; принимает children; поддерживает общий вариант и явный цвет |
| `Divider` | Тонкая линия с настроенным inset; горизонтальный вариант первым, вертикальный добавлять при конкретном переносе |
| `Section` | Заголовок, описание, дополнительные действия и children; не создаёт Surface автоматически |
| `FormRow` | Подпись/описание слева, необязательный leading, control справа; отдельные места содержимого, min-width и перенос длинных описаний |
| `SearchField` | Составляется из TextField и поисковой иконки; принимает тот же input |
| `Picker` | Составляется из MenuChip, существующего dropdown и MenuItem; готовые варианты, selected, disabled, handler |
| `InfoRow` | Подпись и произвольное значение с baseline alignment; общую ширину колонок задаёт родитель |
| `EmptyState` | Заголовок, описание, необязательная иконка и action; обычная композиция без запроса данных |

Surface и Section остаются отдельными: заголовок секции может находиться над карточкой или непосредственно на странице. FormRow также не рисует поверхность карточки. Родитель добавляет разделители между строками; флаг `last` не становится обязательным параметром каждой строки.

FormRow не получает click handler для всего ряда по умолчанию. У checkbox можно сделать подпись частью hit area, но вложенное действие остаётся отдельным. На узкой ширине и при большом тексте сохранить доступ к контролу и перенос описания; не полагаться на одинаковую длину русских и английских подписей.

Первый Picker рассчитан на небольшие меню вроде темы, языка и периода. Для моделей, проектов и веток переиспользовать строку и popover, сохранив существующую фильтрацию и виртуализацию; универсальный searchable picker здесь не нужен.

### 8.3. Действия и диалоги

| Компонент | Контракт и устройство |
| --- | --- |
| `ActionRow` | Leading icon/indicator, подпись, trailing content, role, disabled/loading, стабильный focus, один handler |
| `KeyHint` | Принимает готовую платформенную подпись shortcut; отображает её, не регистрирует key binding |
| `Dialog` | Deferred layer, scrim, Surface, header/body/actions, close/confirm, жизненный цикл фокуса |

Сначала заменить два существующих action row helpers общей реализацией с сохранением размеров, цветов и событий. Потом вынести Dialog. Не объединять эти изменения с переносом commit/goal models или изменением бизнес-поведения.

### 8.4. Списки и навигация

| Компонент | Контракт и устройство |
| --- | --- |
| `Menu`/`MenuItem`/`Popover` | Развить текущий API; сохранить placement, dismissal, flyout, keyboard и handles |
| `SidebarItem`/`SidebarSectionHeader` | Builder над текущим оформлением; произвольный контент, depth, disclosure, selection |
| `SelectableRow` | Leading/content/trailing, selected и highlighted как разные поля; вложенные действия имеют свой focus и propagation |
| `SegmentedControl` | Небольшой готовый список вариантов, selected, on_change; стрелки, Home/End и видимый фокус |
| `TabBar`/`TabItem` | Готовые tabs, active ID, leading icon, подпись, dirty indicator, optional close; отдельная активация и закрытие |
| `DisclosureGroup` | Controlled expanded, header и отложенное построение body; скрытое содержимое не строится на каждом кадре |

Scrollable коллекции используют прежние `list()`, `ListState`, `ScrollHandle` и scrollbar. Рендер строки получает подготовленный row snapshot. Общая строка не сортирует данные, не фильтрует каталог и не создаёт проекцию всей сессии.

Sidebar, picker rows и ActionRow не сводить к одному универсальному Row: у них разные семантика, layout и управление фокусом. Общие primitives выделять по фактическому повтору.

DisclosureGroup отвечает за представление и предложение нового expanded. Обновление transcript caches и переизмерение высоты выполняет владелец. Для дорогостоящего body использовать callback/factory, вызываемый только при expanded, а не заранее построенный child.

### 8.5. Статусы и загрузка

| Компонент | Контракт и устройство |
| --- | --- |
| `Badge` | Подпись, необязательная иконка и общий tone; предметный статус разрешает приложение |
| `InlineNotice` | Иконка, текст/готовое содержимое, tone, необязательное действие |
| `Toast` | Surface и dismiss; готовое содержимое позволяет сохранить выделение и копирование текста |
| `ProgressBar`/`ProgressRing` | Готовая доля заполнения или неизвестное значение; clamp на визуальной границе, цвета/подпись снаружи |
| `Skeleton` | Блоки с размерами и радиусом; родитель собирает форму будущего экрана |
| `Spinner` | Существующий primitive; при необходимости согласовать публичный builder с ControlSize/IconSize |

Проценты, quota thresholds, стоимость, provider colors и форматирование чисел остаются в приложении. Неизвестное заполнение отличать от нулевого; подпись состояния отображает владелец.

Перед вычислением ширины или дуги проверять, что доля конечна. `NaN` и бесконечность отображать как неизвестное значение; конечную долю ограничивать диапазоном 0–1. Это нормализация отображения, а не исправление исходных метрик или стоимости.

Toast timers, hover pause и generations остаются в `notifications/model.rs`. Анимация Skeleton/Spinner использует существующий pulse clock и reduce-motion. Не заводить таймер на каждый placeholder и не добавлять повторяющийся `with_animation`.


Фильтр `ui::` не покрывает поведение экрана; дополнительно запускать его существующие app/input tests по затронутому scope. `gpui/test-support` остаётся только в dev-dependencies: включение этой feature в рабочую сборку меняет flush/redraw поведение. Не добавлять зависимости ради builders или нескольких функций оформления.

### Приложение и визуальные проверки

Считать существующий `bun ./scripts/dev.ts` владельцем `Michelle Debug.app`. После source-изменения дождаться успешной пересборки, подписи и relaunch watcher. Не запускать второй watcher, `scripts/bundle.sh debug` вручную и не закрывать приложение ради relaunch. Восстанавливать watcher только после подтверждения, что он недоступен.

Визуальную проверку выполнять только по запросу пользователя, согласно AGENTS.md. Этот план сам по себе её не разрешает. Когда она запрошена, проверять свежую watcher-сборку: обе темы, увеличенный контент при неизменном UI, длинные подписи, узкое окно, hover/pressed/focus/disabled/loading, края поверхностей, системный шрифт и reduce-motion. Для provider-сценария использовать точное затронутое взаимодействие. Успешная Rust-сборка не подтверждает внешний вид.

Для обычной композиции достаточно реального пилотного экрана и примеров в README. Отдельный showcase-экран или новый executable не входит в обязательную работу.

### Производительность

Правила и measurement playbook брать из [docs/performance.md](docs/performance.md). Сравнивать одинаковые сценарий, объём данных, настройки, сборку и участок streaming до/после.

Записывать:

- Частоту window frames, pane renders и stream commits.
- CPU по этапам потока, а не только среднее за весь ответ.
- Количество видимых layout-элементов и причины изменения вложенности.
- Время открытия меню/диалога и работу row builder для большого списка.
- Возврат в idle после закрытия меню, завершения загрузки и истечения pulse leases.

Принимать перенос, если соблюдены текущие ограничения commits ≤ примерно 8,3 Гц, pulse ticks ≤ 60 Гц, а обычных pulses ≤ примерно 30 Гц; используются более редкие существующие режимы для дорогих поверхностей. Не считать максимум cadence разрешением поднять частоту относительно исходной.

Не использовать повторяющийся `with_animation` и декоративный `request_animation_frame` в streaming path. Не добавлять notify/refresh из stateless render. Тяжёлую подготовку выполнять в существующих моделях на background executor с защитой generations; кадр получает готовый snapshot.

Не задавать выдуманный абсолютный CPU-бюджет для всех машин. Отклонение от исходных результатов разбирать по counters; пользовательские выводы о скорости подтверждать release-сборкой. FPS counter не подходит для измерения streaming cadence, поскольку сам закрепляет redraw на частоте дисплея.

## 12. Как расширять систему после внедрения

Для нового компонента:

1. Найти реальное использование и повторяющийся контракт; сначала проверить готовые компоненты.
2. Определить содержимое, оформление, состояние и владельца операций.
3. Собрать stateless-композицию на существующих primitives, сразу с `TextStyle` и пиксельными метриками без прямой или транзитивной зависимости от `sp()`. Новую entity добавлять только при самостоятельном жизненном цикле или render identity.
4. Реализовать применимые клавиши, focus-visible и hit area одновременно с mouse handler.
5. Добавить export, пример в README, первого потребителя и одну необходимую поведенческую проверку.
6. Проверить source совместимость, тему, фиксированные системные размеры UI, границу контентных метрик и горячий путь, если компонент в него входит.

Локальный компонент переносится в `src/ui`, когда он выражает общий интерфейсный контракт. Два похожих фрагмента с разным предметным поведением могут остаться в своих экранах и разделять только primitives.

Наследование control size, role и styles по поддереву вводить отдельной задачей при доказанном повторе. Пока использовать явные параметры, существующее наследование текста и общий снимок темы. Не эмулировать scope временной заменой global `UiColors`: GPUI может строить потомков в другой фазе. Настоящий scope требует собственного корректного element lifecycle и правил invalidation.

Публичные протоколы стилей рассматривать после нескольких реально разных оформлений одного контрола. Внутренние функции оформления уже дают место для такой эволюции; заранее строить framework для этого не требуется.

## 13. Итоговая приёмка

- [x] Базовые контролы имеют согласованный API и соблюдают описанное style precedence.
- [x] Пилот General/Appearance подтверждает пригодность FormRow, Section и Surface кодом и автоматическими проверками; визуальная пригодность не подтверждена.
- [x] Settings, Skills и оба диалога используют общие компоненты в перечисленном scope.
- [x] Навигация, picker rows, статусы, tabs и горячие контролы переведены по очереди внедрения.
- [x] Нет новых предметных зависимостей в reusable UI, кроме сохранённого существующего backend ввода.
- [x] Новые компоненты и используемые ими общие helpers не зависят от `sp()`; совместимость rem сохранена только у старых callers.
- [x] Theme TOML, persisted settings, drafts и операции сохраняют совместимость.
- [x] Настройка увеличения интерфейса удалена; системные роли UI не зависят от настроек контента или кода.
- [x] Старый размер текста сохранён для контента; rem-база фиксирована, изменения контентных метрик правильно инвалидируют измерения.
- [x] Фокус, keyboard, nested actions и reduce-motion имеют соответствующие доказательства.
- [ ] Перенос горячих путей подтверждён counters и сравнением производительности.
- [x] Заменённые дубли и unused legacy API удалены; intentional GPUI-layout остаётся допустимым.
- [x] README и примеры соответствуют фактическому API.
- [x] Визуальная проверка, если запрошена, выполнена в свежей watcher-сборке; иначе её статус явно остаётся неподтверждённым. Не запрошена, статус неподтверждён.
- [x] Итоговые Rust-проверки пройдены, известные ограничения записаны.

Основные риски: скрытое изменение оформления при слиянии стилей; оставшаяся связь UI с размером контента через rem или общий Markdown helper; потеря пользовательского размера при переименовании; двойное масштабирование контента; второй источник истины у controlled inputs; потеря focus или propagation при вложенных действиях; увеличение количества layout-узлов и redraw cadence. Каждый риск проверяется в этапе, который затрагивает соответствующий механизм.
